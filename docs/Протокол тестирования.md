## Главные бизнес-правила (то, что просили проверить отдельно)

### 1. Один и тот же заказ нельзя отправить несколько раз

| Ситуация | Что делает система | Тест |
|---|---|---|
| Двойное нажатие «Отправить заказ» | Клиент отправляет ключ попытки (`idempotencyKey`); второй запрос возвращает **тот же** заказ, нового не создаётся | ✅ последовательно и одновременно |
| Повтор после обрыва связи | То же: ключ тот же — заказ тот же | ✅ |
| Нажали ещё раз уже с новым ключом | Корзина после заказа пуста → 409 «Корзина пуста, заказ уже в истории» | ✅ |
| Собрали точно такой же заказ на то же судно, пока первый ждёт подтверждения | 409 «Такой же заказ уже ждёт подтверждения: НСРЗ-000…» со ссылкой на него | ✅ |
| Та же деталь добавлена в корзину дважды | Количество складывается, вторая строка не появляется | ✅ |
| Тот же набор на другое судно / после подтверждения первого | Разрешено — это действительно новая закупка | ✅ |

Ручная проверка на сайте: двойной клик по «Отправить заказ» создал ровно **один** заказ (НСРЗ-000155).

### 2. То, что ушло на подтверждение, резервируется

Остаток на складе делится на «зарезервировано» (в заказах со статусами от «ожидает подтверждения» до «готов к выдаче») и «доступно». Заказать можно только доступное.

| Шаг (деталь НСРЗ-ГД-01427, на складе 12 шт.) | Ожидание | Результат |
|---|---|---|
| Судовладелец 1 заказал 10 шт. | резерв 10, доступно 2 | ✅ |
| Судовладелец 2 пытается положить 3 шт. | 409 «доступно только 2 — ещё 10 в резерве» | ✅ |
| Судовладелец 2 заказал 2 шт. | резерв 12, деталь показывается «Всё в резерве» | ✅ |
| Деталь лежала в корзине, а её зарезервировали другим заказом | при оформлении 409, корзина подсвечивает проблему | ✅ |
| Два судовладельца одновременно заказывают последнюю единицу | заказ получает только один, второй — 409 | ✅ |
| Сотрудник отклонил заказ | резерв снят, детали снова доступны | ✅ |
| Сотрудник завершил заказ (выдан) | товар списан со склада, резерв снят | ✅ |
| «Под заказ» | резерв не берётся, склад не ограничивает | ✅ |

Как это устроено: резерв берётся атомарным условным `UPDATE … WHERE quantity - reserved >= N` внутри транзакции, а заказы одного пользователя выстраиваются в очередь через advisory-lock PostgreSQL. Поэтому правило держится даже при одновременных запросах.

**Каталог (13):** поиск по номеру производителя с пробелами; по каталожному номеру в любом регистре; по части номера; по названию (регистр и порядок слов не важны); пустой результат; фильтр по типу судна; фильтр по категории; «только доступные»; три статуса наличия; карточка запчасти; постраничная выдача; справочники; сжатие ответов gzip.

**Заказы (26):** 8 тестов резерва; одновременный заказ последней единицы; 9 тестов защиты от повторов; 5 проверок корзины и оформления (нет на складе, под заказ, неверное количество, чужое судно, фиксация цены); 3 теста изоляции данных и экспорта CSV.

**Панель НСРЗ (20):** очередь (старые первыми); новый заказ сразу в очереди; нельзя перескочить статус; нельзя отклонить без причины; синхронизация статуса; одновременное нажатие двух сотрудников; завершение списывает товар; из «завершён» переходов нет; отклонение с причиной; SMS о смене статуса; ручное обновление остатка; статус «под заказ»; неверное количество; остаток меньше резерва — предупреждение; поиск в остатках; загрузка CSV с ошибками по строкам; файл без нужных столбцов; шаблон CSV; статистика; компании и пользователи.

## Ограничения

- Нагрузочное тестирование не проводилось (пилот — 10–20 судовладельцев).
- Скорость на канале 128 кбит/с отдельно не замерялась: ответы API сжимаются, выдача постраничная.
- iOS: нативная сборка без Mac невозможна; на iPhone проверяется веб-версия приложения (та же кодовая база Flutter).
- Реальные SMS и письма не отправлялись: работает демо-режим с журналом уведомлений. Подключение реальных сервисов — заполнить ключи в `backend/.env`.
